# Password work limits and authentication throttling API specification

**Status: Approved and implemented, 2026-10-14.** The user approved this specification and authorized implementation under [AGENTS.md](../../AGENTS.md). Password work, public request admission, source attribution, and client error handling passed the acceptance checks below. The values are operating policy choices, not a measured RAM or throughput guarantee. Deployment and production proxy activation require separate explicit authorization.

**Follow-up:** The separately authorized [2026-10-16 hardening contract](backend-hardening-spec.md) adds complete auth-body limits, persisted OTP guess budgets, and password-change session revocation. This document retains the original packet’s approval and evidence; [API.md](../API.md) describes current behavior.

## Scope and implementation

Before this packet, [registration and login](../internal/handlers/v1/auth.go) called the password helpers without concurrency admission, [password changes](../internal/handlers/v1/user.go) performed two separately unguarded operations, and public auth JSON was bound without request throttling. The [password service](../internal/utils/password.go) now owns the shared reservations and guarded helpers; new hashes retain 64 MiB Argon2id parameters, and comparison retains parameters embedded in stored hashes. The [public admission middleware](../internal/middlewares/auth_rate_limit.go) applies the separate [request limiter and source resolver](../internal/authlimits/) before JSON binding. [Handler resource helpers](../internal/handlers/v1/auth_resources.go) handle reservation refusal and cancellation.

This packet covers `POST /v1/auth/login`, `POST /v1/auth/register`, the password-work portion of `PUT /v1/user/password`, a shared admission service, safe source attribution, and client handling of two new errors. Existing routes, JSON fields, validation tags, token lifetimes, password-hash strength, and credential/conflict responses remain. [API.md](../API.md) owns the implemented wire contract; this document owns the approved policy and acceptance requirements. Acceptance evidence is recorded below.

This packet makes no database/schema change, adds no external dependency or distributed limiter, and does not change account lockout, password normalization, dummy hashing, or session revocation. Request-body byte limits and OTP guessing budgets remain separate work. These controls do not bound HTTP body decoding, all database work, or total process memory.

## Approved policy

| Control                                | Initial value                              | Applies to                                                                    |
| -------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------- |
| Shared password-work reservations      | **2 per process**                          | Registration, login, password changes, and every other password helper caller |
| Waiting queue for reservations         | **0**                                      | Reject immediately when both reservations are occupied                        |
| Login admissions per source            | **10 in a rolling 60 seconds**             | Public login, regardless of identifier or result                              |
| Registration admissions per source     | **3 in a rolling 60 seconds**              | Public registration, regardless of identifier or result                       |
| Combined public auth admissions        | **60 in a rolling 60 seconds per process** | Login and registration together, across sources                               |
| Source records retained by the limiter | **At most 10,000 per process**             | One canonical source-IP record containing both endpoint histories             |

The values are named policy constants for this packet, with isolated injectable policies/clocks in tests. There are no runtime quota/concurrency tuning variables. A change to production values requires a revised approved policy. With only admitted requests stored, the combined 60-request budget ordinarily bounds active source records far below the defensive 10,000-record ceiling.

Two current-format Argon2 operations use approximately 128 MiB of working memory together. This is not a process-memory ceiling: stored legacy parameters, other allocations, and garbage collection affect peak use. Preserve supported stored-hash parameter compatibility; this packet does not introduce a parameter ceiling. Capacity/load measurements must be reported before making stronger memory or latency claims.

All state and budgets are process-local. A process restart resets request history; multiple instances multiply the effective quota and reservation budget. The gate protects each instance without promising cluster-wide enforcement or fair access during sustained overload. Public IP sharing through NAT and proxies also shares source quotas. Distributed coordination and account-specific guessing policy require separate approval.

## Trusted source attribution

Quota keys must come from the TCP peer or a verified proxy chain, never directly from a client-supplied header. The [current startup](../cmd/api-server/main.go) does not override Gin's trust-all proxy default; using current `ClientIP()` unchanged would make source quotas forgeable. [Gin's proxy guidance](https://gin-gonic.com/en/docs/server-config/trusted-proxies/) describes explicit trusted-proxy configuration.

The approved optional backend startup setting, `AUTH_TRUSTED_PROXY_CIDRS`, contains a comma-separated allowlist of proxy CIDRs. Empty/unset means **no trusted proxies** and direct-peer attribution. Validate every CIDR before database startup or opening the listener; reject malformed values and `/0` trust-all prefixes, including equivalent IPv4-mapped trust-all ranges. Never infer trust from private or Docker address ranges. This configures the auth source resolver only; it must not delegate identity to Gin's existing `ClientIP()` or change other routes' proxy behavior. Public auth logs use the resolver's source value so recorded decisions match quota identity.

The setting has empty-default passthrough in [root Compose](../../docker-compose.yaml), [backend Compose](../docker-compose.yaml), [root environment template](../../example.env), and [backend environment template](../example.env), with setup owned by [deployment](../../DEPLOYMENT.md#authentication-source-attribution) and [backend development](../README.md#authentication-source-attribution) guides. No production allowlist is supplied by this packet.

Forwarded attribution is allowed only when the actual TCP peer belongs to the explicit allowlist. Accept only `X-Forwarded-For`. Combine **all** header field values in received order with commas, then validate every comma-separated element as an IP before selecting one; a first-field-only read or partial chain validation is insufficient. Empty elements or malformed chains fall back to the validated peer. For a valid chain, inspect right to left, skip approved proxy hops, and select the closest untrusted address; if all hops are trusted, use the leftmost supplied address. Ignore `X-Real-IP`, `CF-Connecting-IP`, platform shortcuts, and forwarding headers from untrusted peers. Unsupported/missing peer identity must not inherit Gin's implicit Unix-socket trust or fall back to arbitrary headers.

Normalize IPv4-mapped IPv6 to IPv4, use a canonical IP representation, and exclude TCP ports and IPv6 zone identifiers from keys. A request whose transport peer cannot be validated receives `500 INTERNAL_SERVER_ERROR` before body parsing, quota mutation, account lookup, or password work.

The deployment owner must verify that each approved proxy constructs or sanitizes the forwarding chain. CIDR membership alone cannot prove header provenance. Until an allowlist and that behavior are explicitly approved, users behind Cloudflare Tunnel/reverse proxies share the proxy peer's quotas: **10 logins and 3 registrations per minute for that peer**. This is an approval tradeoff, not per-user fairness. Global and health-route behavior must not accidentally depend on a forged header.

## Request throttling rules

Install one shared limiter on the two registered public POST routes, before JSON binding and account lookup. Health, refresh, logout, email verification, password changes, unknown routes, other methods, and CORS preflights do not consume these public request quotas. Password changes still participate in the password-work gate after existing bearer authentication and body validation.

Use the rolling interval `(now - 60 seconds, now]`. An admission exactly 60 seconds old has expired. Evaluate endpoint/source and combined-process quotas under one mutex, then append to both applicable histories atomically. Use monotonic elapsed time for production windows; wall-clock adjustment must not prematurely refill quotas.

Every **admitted** public request consumes its source/endpoint and combined quota, including malformed JSON, successful login/registration, invalid credentials, conflicts, database/hash failures, and a later password-capacity `503`. Success does not reset history. A quota denial, unresolved peer, or source-store capacity denial appends nothing, extends no expiry, and allocates no new record. Cancellation already observed before throttle admission also appends nothing; cancellation after admission does not refund quota. Changing usernames, email aliases, passwords, or connection ports cannot obtain a new source budget.

Prune expired timestamps and source records, then evaluate all applicable quotas without allocating a new record. An exhausted quota returns `429`, including when the source-record ceiling is also full. Only if quotas allow admission may a needed new record at the ceiling return capacity `503`. Retain bounded histories only; do not retain unbounded backing storage or raw identifiers. Preserve active quotas; do not evict a live record or use a shared fallback key. Existing-source requests can proceed if their quotas allow. Append histories only after both quota and store checks succeed. The combined history is bounded by its limit.

For quota denial, calculate the earliest time when **all currently blocking quotas** permit one admission, take the maximum of their release times, and return ceiling-rounded remaining seconds, minimum one. Denials do not extend that time. New concurrent traffic can consume capacity again, so `Retry-After` is guidance, not a reservation.

Source keys deliberately do not contain account identifiers. This prevents an identifier-only throttle from locking out a named victim and avoids alias inconsistencies. It does not close every distributed password-guessing or existing account-enumeration path.

## Password-work reservations

After public throttling and successful body validation, acquire one reservation **before any account-specific lookup or conflict check**. When saturated, syntactically valid known/unknown login identifiers and fresh/existing registration identifiers receive the same capacity response without lookup. Existing invalid-body responses still occur before work admission. The reservation includes those lookup/precheck stages so lookup timing cannot select a different busy response.

Registration holds its reservation through conflict checks and hash creation, then releases before account persistence/token issuance. Login holds it through lookup and password comparison, then releases before token issuance. Unknown users or conflicts release without running Argon2. Password changes acquire after authentication/body validation and hold **one reservation across both** old-password comparison and replacement hashing; do not reacquire or return busy between those two operations. Release before the final password database write.

The admission service must own the worker/reservation lifecycle. Raw Argon2 primitives remain private or reachable only through an active reservation. All callers of the existing helpers must use the shared service, including future internal callers; handlers must not create independent gates or double-acquire through utility wrappers. An operation after a reservation has closed is refused, and closing is idempotent. One reservation cannot run multiple Argon2 calls concurrently.

Pass request context through admission, affected lookups, and password work. Check cancellation before reservation/work starts and between the two password-change operations. Once Argon2 starts, it is synchronous work that retains its reservation until the worker actually returns or unwinds. Client cancellation, HTTP timeout, or a detached caller must not release capacity while computation continues. Do not create a background hash goroutine that outlives a released permit. Release reservations on every exit path, including errors and panic unwinding.

Check cancellation immediately after each synchronous worker returns and before subsequent account/password writes, token issuance, and success emission. After cancellation is observed, do not start another hash or those later steps. Propagate context cancellation to the handler; no new `499` or guaranteed response is specified for a disconnected client. Already-started database operations can have uncertain outcomes; this packet does not promise transactional rollback of all existing auth side effects.

## Responses and precedence

Retain the [existing error envelope](../internal/common/response.go). Add two codes to the [error catalog](../internal/common/error.go):

| Condition                                                                                | Status and body                                                                                                   | Headers                                                              |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| A public endpoint/source or combined request quota is exhausted                          | `429`, `{ "code": "AUTH_RATE_LIMITED", "error": "Too many authentication requests. Please wait and try again." }` | Calculated positive integer `Retry-After`; `Cache-Control: no-store` |
| Both password reservations are occupied, or a new source cannot fit after expiry pruning | `503`, `{ "code": "AUTH_CAPACITY_EXCEEDED", "error": "Authentication is temporarily busy. Please try again." }`   | `Retry-After: 1`; `Cache-Control: no-store`                          |
| A transport source cannot be resolved safely                                             | `500`, existing `INTERNAL_SERVER_ERROR` envelope                                                                  | `Cache-Control: no-store`                                            |

The one-second capacity retry interval is conservative guidance; it does not promise a free worker at that time. Responses disclose no account existence, quota bucket, active-worker count, or credential data. [429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) represents request throttling; [503](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4) represents temporary service capacity refusal.

Public response precedence is source attribution, request throttle/store admission, existing JSON validation, password reservation, then existing credential/conflict/hash/database/token outcomes. Thus an over-quota malformed request gets `429`, an admitted malformed request gets existing `400`, and an admitted valid request at work saturation gets `503`. The latter still consumed request quota; a throttle/store denial did not. Protected password changes retain authentication and validation precedence before reservation, followed by existing old-password and persistence outcomes.

Public admission refusal performs no account lookup, password computation, token issuance, or account/password mutation. Protected password changes may already have completed existing authentication/user loading before capacity refusal; refusal performs no password computation, final password write, or token issuance. Work-capacity refusal is returned as `503`, never disguised as `401`, `PASSWORD_HASH_FAILED`, or a generic hash `500`. Actual hash-format/worker failures retain current non-capacity errors. Existing successful token-pair and password-change responses remain. Existing non-cancellation login lookup-error classification is not redesigned by this packet.

Expose `Retry-After` to existing allowed browser origins through CORS without changing allowed origins, methods, or credential policy. Add localized messages for the two new machine codes through the existing [error mapping](../../frontend/src/lib/errorLocalization.ts) and all five locale catalogs. A timer/countdown, automatic credential retries, or automatic registration resubmission is not part of this packet. Existing clients retain a valid error envelope and generic fallback handling.

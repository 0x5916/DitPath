# Learning evidence V1: additive API RFC

Status: **APPROVED for additive implementation on 27 October 2026** by the human repository owner. Prepared against `dev` baseline `1e8e4d4`. Implementation is phased below; approval does not authorize deployment or alteration of existing contracts. [Pilot policy 1.0](../../frontend/docs/learning-policy.md) owns learning criteria. [Approved training-history V1](training-history-v1-spec.md) remains authoritative for the current API.

## Decision and compatibility boundary

Use a separate, authenticated evidence ledger and feed. Preserve existing guided/practice attempts, session manifests, legacy history, bearer ownership, V2 aliases, and the old snapshot verbatim. Do not add new kinds to the existing `/training/changes` feed: [the current client parser](../../frontend/src/lib/training-wire.ts) rejects unfamiliar kinds, prompt kinds, and input modes.

| Can ship without a backend change                                                                                                                        | Cannot honestly use the existing contract                                                                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pure policy/tests; truthful labels; historical estimates based on existing fields; separately stored local coaching/screening and later local assessment | Purpose-aware coaching/screening in synchronized history; proof of planned mixed checks/first opportunities; reference or unchecked-practice exposure; new scoped awards and their corrections |

[Existing event serialization](../../frontend/src/lib/training-wire.ts) and [server storage](../internal/training/history_store.go) select known fields; arbitrary sidecars do not round-trip. [Strict event schema 2](../internal/handlers/v2/training_strict.go) is immutable and cannot be enriched after ingestion. [Session validation](../internal/common/training_sessions.go) permits only guided `koch-39-v1` lessons or completed practice with counts 1/1, no event manifest, and `practice-copy-v1`. Therefore neither an unmeasured “Lesson N” nor a fabricated passage score is a truthful representation of a coaching round. A newer fake guided session can also obscure unfinished work in the [local session selector](../../frontend/src/lib/data/session-repository.ts).

## Approved scope and rollout

Approval of this RFC covers additive evidence storage, the two endpoints below, structural validation, server evidence projection, and client integration in discrete packets. It would not approve changing authentication, existing snapshot semantics, old scoring, dependencies, deployment configuration, or V2 retirement.

1. Local pilot: new owner-scoped database; coaching/screening only; no backend writes for these sessions. Label device-only storage. Existing application history remains untouched.
2. Add the ledger/feed and synchronize purpose-aware plans, observations, exposures, and terminal manifests. Coaching/screening never awards milestones. Show old clients their unchanged history.
3. Enable prospective mixed checks and full exposure capture across guided, reference, coaching, and contextual playback. Enable synchronized milestones only after server/frontend parity, late-data correction, timing-uncertainty, and complete-history acceptance pass. Do not award retroactively from metadata-poor legacy events.

The client must treat 404/unsupported schema as an unavailable feature, retaining local evidence without retry loops or falling back to old event endpoints. Unsupported storage is not synchronized. No automatic deletion or replacement of old records occurs.

## Additive endpoints

Both use existing bearer authentication and user-loading middleware. Account ownership comes only from authentication; reject `user_id`/`owner_key` in request envelopes and records. `client_id` is diagnostic installation identity, not authorization.

| Endpoint                                     | Proposed contract                                                                                                                                                                                                                                                                                                                  |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/training/learning-evidence/batch`  | Envelope `schema_version: 1`, nonzero UUID `client_id`, optional RFC3339 `client_sent_at`, and `records` (1–100). Maximum body 256 KiB. Return 200 `{acknowledged_ids, rejected_records}` with each rejection `{id,error_code,message,retryable}`. Valid siblings may commit; storage failure returns 500 without acknowledgement. |
| `GET /v1/training/learning-evidence/changes` | Opaque `cursor`, `limit` 1–100/default 100. Return `{changes,next_cursor,has_more}`; each change has ascending string `revision`, `kind`, immutable `record`. Complete response at most 1 MiB. Server-derived milestone/correction records appear only in this feed.                                                               |

Use a separate per-account feed revision/epoch and distinct HMAC signing domain. Capture a committed ceiling when paging; return a checkpoint even when drained. Bind cursors to account and epoch; a stale epoch returns 410 `LEARNING_EVIDENCE_CURSOR_RESET_REQUIRED`. Malformed/wrong-account cursors return 400 `INVALID_QUERY_PARAMETER`. Clients commit each page/checkpoint atomically and preserve pending uploads on reset. Do not change the existing history cursor or its feed epoch.

## Current phase availability

The ledger packet admits `plan`, `observation`, `exposure-open`, `exposure-close`, and `terminal`. Plan purposes enabled now are `coaching` (12 prompts) and `screening` (8 prompts), with immediate feedback. The local frontend purpose `return-screening` maps explicitly to wire `screening`; it is not sent to the old practice API. Coaching uses three occurrences of each pair member plus six other taught anchors when available, or six of each pair member when no anchors exist. Target/anchor roles must match that allocation. Screening samples `min(8, taught-set size)` distinct sounds across eight prompts; these target roles indicate sampled sounds, not certification.

The dev implementation now admits structurally valid `mixed-check` plans, bounded per-target `review_cycle_ids`, and mixed exposure records. Client milestone/correction submissions remain forbidden. Account-locked ingestion runs the versioned server projection and appends its claims/corrections in the same transaction; a projection failure rolls back the submitted batch and its watermark. Deployment has not been authorized by this RFC. Acceptance evidence and remaining device/service gates are recorded in the [P1 report](../../frontend/docs/reports/2026-10-27-learning-evidence-p1.md).

## Client record schema 1

Each record has `id` (nonblank native ID, at most 128 UTF-8 bytes, no NUL or `legacy:` prefix), `kind`, `policy_version`, and `recorded_at` (RFC3339, year 1–9999). Timestamp normalization uses UTC microseconds. Pin `policy_version` to `learning-policy-1.0`; unsupported policies reject explicitly. Correctness and awards are derived, never accepted as client booleans.

A `time_bounds` object is `{earliest,latest,source}` where times are RFC3339 and earliest <= latest; `source` is `monotonic-anchored` or `wall-clock-bounded` when bounds are known. Unknown is represented by null bounds, never a zero-width claimed instant. Process/clock diagnostic extensions need a later schema; current records use the bounded times only; neither server receipt nor a client clock assertion proves a practice gap. Bounds crossing a threshold cannot qualify it.

| Kind             | Required payload and semantics                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `plan`           | `session_id`, `purpose` (`coaching`, `screening`, `mixed-check`), `curriculum_version: koch-39-v1`, `profile` (`id`, `task: single-character`, `char_wpm`, `audio_condition: clean`, `response_support: open`), exact playback settings, `started_at`, `introduced_characters`, `targets`, ordered `prompts` (`id`, `character`, `role: target or anchor`), `fresh_order`, `feedback` (`immediate`or`after-check`), and optional per-target `review_cycle_ids`. Maximum 100 prompts; IDs unique, characters from the existing 40-character curriculum, targets drawn from the taught set. Each plan is immutable. Mixed-check limits and feedback rules follow pilot 1.0.                        |
| `observation`    | `session_id`, `prompt_id`, `presentation_id`, `first_response` and `final_response` (nullable normalized text, at most 64 characters), explicit `skipped`, `replay_count_before_response` (null or integer 0–1000), nullable `help_before_response`, `audio_valid`, `interruption_invalidated`, `response_interface` (`keyboard`, `full-alphabet`, `restricted`), `first_presented_at` bounds, `prior_exposure` bounds, and actual playback settings. Optional `legacy_attempt_id` links a genuine existing guided attempt but does not alter it. One canonical first observation per plan/prompt and one observation per owner/presentation; a correction never overwrites that first response. |
| `exposure-open`  | `session_id` nullable, `presentation_id`/action identity, `characters` (unique known symbols), `source` (`guided`, `reference`, `coaching`, `screening`, `mixed-check`, `group`, `word`, `callsign`), and `started_at` bounds for guard/user-action initiation, which may precede actual tone scheduling by storage preparation. Persist before any potentially audible action. This conservative guard is not proof that playback succeeded. Batch by playback/feedback action, not tone.                                                                                                                                                                                                       |
| `exposure-close` | `open_id`, `end_reason` (`completed`, `stopped`, `recovery`), and per-character `last_exposure` bounds. It closes exactly one same-owner open action with the same character set. Use actual last-played bounds or a conservative end-of-playback bound. One immutable closure per open action; unknown bounds remain unknown. No initial playback timestamp may substitute for its ending.                                                                                                                                                                                                                                                                                                      |
| `terminal`       | `session_id`, `status` (`completed`, `abandoned`, `incomplete`), nullable `ended_at` (required for completed), and a unique sorted `observation_ids` manifest. The manifest must equal the accepted observations for that plan. Counts, outcomes, and qualification are server-derived. A completed mixed check requires the entire planned opportunity set; invalid delivery may produce an incomplete check, not replacement trials hidden in a finished manifest.                                                                                                                                                                                                                             |

Policy-scoped goal IDs must match their fields; clients cannot relabel an old profile while retaining its ID. Character/effective speeds stay 5–50 with effective <= character, pitch 300–2000 Hz. Null evidence-quality fields remain unknown and cannot certify new milestones. Plans for coaching/screening can share the same goal context but never count as mixed checks. The server does not treat `fresh_order: true`, claimed prior-exposure bounds, or an upload's success flag as sufficient proof: verify the plan and recompute against accepted evidence. Unknown external practice remains outside the claim.

Upload plan and exposure-open before dependent observations/closures; upload observations and known closures before terminal. A terminal manifest may record an incomplete action; it cannot qualify a delayed claim while relevant exposure bounds remain unresolved. A not-yet-accepted dependency is retryable `MISSING_EVIDENCE_DEPENDENCY`. A contradictory owner, manifest, prompt, or terminal dependency is permanent `EVIDENCE_SET_CONFLICT`. No new observations may be appended to a finalized plan. Identical normalized retries acknowledge without a new revision; changed content at the same account/ID returns `ID_CONFLICT`. The same prompt cannot gain another first response through a new observation ID. Records outside a genuine referenced legacy attempt's authenticated owner/session/prompt reject.

Additional errors (including the current phase gate `FEATURE_NOT_ENABLED`): `INVALID_RECORD`, `INVALID_TIME_BOUNDS`, `UNSUPPORTED_POLICY_VERSION`; envelope errors use existing `{code,error}` conventions with 400 unsupported schema/body, 413 size, and 500 persistence failure. Temporary 429/5xx errors retain local work and honor Retry-After. No record-level rejection permits dropping its dependent pending work silently.

## Exposure completeness and clock limits

Persist `exposure-open` before starting a potentially audible action and append `exposure-close` only after its end is known. A crash/interruption leaves the open guard unresolved and blocks a precise later gap. On recovery, stop/dispose the prior audio resources before recording a conservative closure whose latest bound is that recovery time; do not backdate it to the last known start. An unresolved action from another device remains uncertain until a closure arrives. Closure can follow terminal history, because it supplies exposure chronology rather than appending another assessed attempt.

An observation may begin after its guard without overlapping its start bounds. Reject only definite reversal (tone entirely before the guard), or a tone entirely after a known closure end; validate the latter in either upload order.

For each first probe, derive the latest relevant exposure before that presentation from all available accepted records, including other modes/devices. Treat the submitted `prior_exposure` as a diagnostic snapshot to reconcile, not authority. Within-block later presentations do not retroactively change its frozen pre-block boundary. A late prior exposure triggers re-evaluation. Receipt order determines sync revisions, not pedagogical chronology. Old/uninstrumented histories and incompletely synchronized devices cannot prove comprehensive absence; UI claims remain scoped to available recorded history.

## Server-derived claims and corrections

After a complete compatible manifest, run the versioned pure projection against canonical evidence in the account transaction. Validate eligible counts, assistance, purpose/profile, cold first probes, elapsed bounds, and due-cycle consumption. Keep frontend/backend fixtures identical; do not reuse the existing latency-gated mastery snapshot as the pilot verifier.

Emit server-only `milestone` records with stable `id`, `character`, `profile`, `milestone_kind` (`proficiency`, `retention`), `policy_version`, `awarded_at`, supporting plan/observation/exposure IDs, measured gap bounds, scope, and source-revision watermark. Coalesce visible milestones by account + goal scope + kind + policy; preserve supporting claims and show earliest valid attainment. No client-supplied award is accepted.

Server claim identities use the reserved `legacy:lp:m:` namespace followed by a deterministic basis hash; corrections use `legacy:lp:c:`. Client native IDs cannot occupy either namespace. A `milestone` contains `character`, the snake-case wire `profile`, `milestone_kind`, `awarded_at`, `check_ids`, `observation_ids`, `exposure_ids`, `gap_bounds`, `scope: available-recorded-history`, and decimal-string `source_revision`, in addition to the common record envelope. Each gap item contains `check_id`, `minimum_ms`, `prior_exposure`, and `first_presented_at`. The evidence IDs include the first-delivery guards and closures; an acknowledged observation alone is insufficient to certify completed delivery.

A `milestone-correction` contains `milestone_id`, `status`, `reason`, `evidence_ids`, decimal-string `source_revision`, and nullable `replacement_id`. The supported pairs are `unverified` / `late-evidence-invalidated` and `superseded` / `earlier-attainment-found`. A pending unresolved exposure guard makes the client projection uncertain; the server defers an irreversible correction while that guard's closure can still settle the evidence. Historical policy-1.0 decoding is independent of future intake gates. Review rungs remain deterministic replayed projections; no mutable client rung or recommendation is accepted as an authoritative claim.

Emit append-only `milestone-correction` records referencing the prior claim, the triggering evidence IDs, and status `unverified` or `superseded`, with a reason and revision. Later mistakes or time passing do not revoke historic attainment. Late evidence that invalidates the original qualification does require an explicit correction; never delete the historical claim or continue presenting it as verified. Server acknowledgement means stored, not perfect observational coverage. Offline local claims remain provisional until their dependencies and server-derived claim are downloaded.

Review cycles are derived from the same canonical history. Two devices consuming one cycle produce one positive rung transition. Unknown chronology never yields an extra rung. Projection caches carry policy/revision watermarks and can be rebuilt; raw evidence and claims survive beyond current-view windows. Existing 30/60-day history views remain unchanged and cannot truncate the new ledger's historical award basis.

## Additive storage and acceptance

Additive PostgreSQL tables: `learning_evidence_records` (account/record ID unique, kind, policy, canonical JSON, hash, client identity, receipt time, revision), `learning_evidence_sync_state` (account revision/epoch), and `learning_evidence_changes` (account/revision immutable payload). A validated dependency index may be additive. Use the existing per-account transaction locking conventions; raw records, derived claim/correction, and their revisions commit atomically. Do not alter existing event/session equality or backfill fabricated assessment metadata. New account deletion follows existing account ownership/cascade behavior; no new deletion endpoint is proposed.

Acceptance before rollout: old-client schema1/2 uploads, frozen session retries, snapshots, and changes remain identical; invalid/new metadata cannot enter old feeds; missing dependencies and reordering recover; retries and multiple devices duplicate no first attempts/claims/rungs; invalid audio and assistance remain distinct; late exposure produces an auditable correction; clock uncertainty does not certify gaps; policy/profile mismatches do not merge; account switches/imports never mix ownership; unknown legacy records produce no new award; local save and cloud sync status are distinct; coaching/screening keep truthful history labels and never alter old lesson/practice counts.

Exposure guard/closure capture on every relevant playback path is a release gate for delayed claims. The local coaching/screening packet can proceed independently while synchronized assessment and milestone activation remain gated.

## Verification environment

The pre-change PostgreSQL baseline on 27 October 2026 had three offset-sensitive assertions under macOS local time (`Asia/Singapore`): `TestCombinedSettingsPostgresAssociations`, `TestForumThreadPostgresLiveCountAndSoftDeletion`, and `TestTrainingBatchDuplicatesPreserveAcknowledgementsAndActivity`. They compared literal `Z` timestamps against the same instants formatted with `+08:00`. Setting the PostgreSQL DSN timezone alone did not change the host-side formatting. No unrelated response contract was changed to accommodate these assertions.

The initial ledger packet's complete post-change suite ran with `TZ=UTC` against the explicitly provisioned disposable PostgreSQL database: 1,253 test/subtest passes across 13 packages, no test skips, exit 0; `go vet` exited 0. Additional focused ledger regressions exercise concurrent identical uploads (both acknowledge; one record/revision), concurrent conflicting IDs (one acknowledgement; one conflict), and a new commit during fixed-ceiling pagination, including a late client occurrence timestamp. This environment choice is verification context, not a deployment configuration change.

The subsequent mixed-assessment and projection integration is verified in the [P1 implementation report](../../frontend/docs/reports/2026-10-27-learning-evidence-p1.md), including its remaining real-client and device acceptance gates.
